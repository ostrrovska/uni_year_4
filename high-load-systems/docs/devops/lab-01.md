# DevOps · Лабораторна 1 — Контейнеризація проєкту

**Проєкт:** CDN Control Plane API — бекенд оркестрації мережі розподілених edge-вузлів
(FastAPI + PostgreSQL).
**Репозиторій:** `high-load-systems/` (той самий проєкт розвивається паралельно для курсу
«Інженерія високонавантажених систем»).

---

## 1. Обґрунтування вибору проєкту

Завдання дозволяє взяти власний проєкт, що задовольняє вимоги a–d. CDN Control Plane API
підходить повністю:

| Вимога | Як виконано |
|---|---|
| **a.** Будь-яка мова / технології | Python 3.13, FastAPI, SQLAlchemy 2 (async), Alembic |
| **b.** Веб-додаток, що взаємодіє з БД / інфраструктурою | HTTP API (FastAPI) поверх **PostgreSQL 16**; міграції через Alembic |
| **c.** Юніт / інтеграційні тести | **39 інтеграційних тестів** у [`tests/`](../../tests/) — ганяються проти реального Postgres (потрібно для Лаби 2) |
| **d.** Кілька частин *(в ідеалі)* | Стек із **4 сервісів**: `postgres`, `migrate`, `api`, `agents` — окремі деплой-юніти, готові до масштабування в наступних лабах |

Домен обрано так, щоб у нього був справжній high-load-профіль (тисячі edge-вузлів, потік
heartbeat-ів + масові запити маршрутизації) — це робить осмисленими майбутні лаби про
масштабування та кешування.

---

## 2. Архітектура як «декілька частин»

Хоча код живе в одній кодовій базі, у продакшн-топології (`docker-compose.yml`) це **окремі
контейнери з різними ролями та життєвими циклами** — саме той поділ, який DevOps-лаба
очікує від «кількох частин»:

| Сервіс | Роль | Тип | Життєвий цикл |
|---|---|---|---|
| `postgres` | Сховище стану (інфраструктурний елемент) | PostgreSQL 16-alpine | довгоживучий, том `pgdata` |
| `migrate` | Накат схеми (`alembic upgrade head`) | one-shot job | `restart: "no"`, відпрацьовує раз до старту API |
| `api` | HTTP-сервіс (FastAPI/uvicorn) | довгоживучий | масштабується `--scale api=N` |
| `agents` | Фоновий воркер, що імітує агентів edge-серверів (`scripts.refresh_fleet --watch`) | довгоживучий | `restart: unless-stopped` |

Додатково є профільовані сервіси: `seed` (профіль `demo` — засів демо-фліту) і `refresh`
(профіль `tools` — одноразовий раунд heartbeat).

> **Чому міграції — окремий one-shot сервіс, а не хук старту API.** Якщо запустити
> `--scale api=N`, кожна репліка інакше кинулася б накатувати ту саму міграцію на ту саму
> БД (гонка). Виконання рівно раз, перед стартом реплік, прибирає гонку — це те, що робить
> можливими лаби про горизонтальне масштабування без переробки цього файлу.

Порядок підняття гарантується залежностями:
`postgres` (healthy) → `migrate` (completed successfully) → `api` та `agents`.

## 3. Dockerfile

Файл: [`docker/Dockerfile`](../../docker/Dockerfile) — **багатостадійна** збірка.

- **Стадія `builder`** (`python:3.13-slim`): ставить `build-essential` і компілює залежності
  у wheels (`pip wheel … -r requirements.txt`). Компілятор потрібен лише тут.
- **Стадія `runtime`** (`python:3.13-slim`): ставить wheels без індексу (`--no-index`), тож
  у фінальному образі немає тулчейну; додає лише `curl` для healthcheck. Створює
  **непривілейованого користувача `app` (uid 1000)** і працює під ним (`USER app`).
- Копіюються лише runtime-артефакти: `alembic.ini`, `migrations/`, `app/`, `scripts/`.
- `HEALTHCHECK` б'є в `GET /health` (liveness). Готовність (`/health/ready`, що торкається
  БД) навмисно поза Docker-healthcheck — її опитує балансувальник, не рантайм контейнера.
- Запуск: `uvicorn app.main:app --host 0.0.0.0 --port 8000`.

Один Dockerfile обслуговує всі сервіси застосунку (`api`, `migrate`, `agents`, `seed`) —
вони відрізняються лише командою запуску (`command:` у compose), а не образом. Це свідоме
рішення: спільний образ = один артефакт для збірки й тестування, різні ролі — через команду.

## 4. docker-compose

Файл: [`docker-compose.yml`](../../docker-compose.yml). Піднімає **весь стек разом**,
включно з базою даних:

- `postgres` з `healthcheck` (`pg_isready`) і томом `pgdata` для персистентності.
- `migrate` — накат схеми, стартує лише коли `postgres` став healthy.
- `api` — стартує лише після успішного завершення `migrate`; порт `8000:8000`.
- `agents` — фонові heartbeat-и, стартує після `migrate`.
- Спільна bridge-мережа `cdn_net`; конфіг сервісів інжектиться через `environment`
  (YAML-anchor `x-api-environment`).
- Порт Postgres на хості — `5434` (бо `5432` зайнятий нативним Windows-сервісом, а `5433`
  — контейнером іншого проєкту). Усередині мережі — завжди `postgres:5432`.

## 5. Команди — збірка та запуск

```bash
# Збірка образу застосунку
docker compose build

# Підняти весь стек: postgres + migrate + api + agents
docker compose up -d

# (Опційно) з демо-флітом edge-вузлів
docker compose --profile demo up -d

# Перевірка, що API живий і готовий (БД піднята)
curl http://localhost:8000/health         # liveness  -> 200
curl http://localhost:8000/health/ready    # readiness -> 200 (503, якщо БД лежить)

# Стан сервісів
docker compose ps

# Зупинити й прибрати все разом із томом БД
docker compose down -v
```

Документація API після старту доступна на `http://localhost:8000/docs`.

### Тести (знадобляться в Лабі 2)

```bash
docker compose up -d postgres          # достатньо самої БД
pytest                                 # 39 інтеграційних тестів
```

Тести піднімають окрему БД `cdn_control_plane_test` (див. `TEST_DATABASE_URL` у
[`tests/conftest.py`](../../tests/conftest.py)).

## 6. `.dockerignore`

Додано [`.dockerignore`](../../.dockerignore), щоб у build-context не потрапляли `.venv/`,
`.git/`, кеші (`.pytest_cache/`, `.ruff_cache/`), `tests/`, `docs/` та локальний
`config/.env`. Це пришвидшує `docker compose build` і тримає локальні секрети подалі від
Docker-демона. На вміст фінального образу не впливає — Dockerfile і так копіює лише явні
runtime-шляхи.

The last one is the interesting one: 64 users hit a flushed key and produced three queries, not 64 — one per instance. More on that in Theory.

How a cached read actually flows

Cache-aside: the application owns the cache. Redis never sits in the write path, which is the whole reason it can die without taking the API with it.

Third path, not drawn: if Redis is unreachable the circuit breaker opens and the lookup is skipped entirely — straight to PostgreSQL, header X-Cache: BYPASS. BYPASS means the cache was never consulted, which is a different statement from MISS, and reporting them separately is what makes the failure demo legible.

Order-independentParameters are sorted before hashing, so ?a=1&b=2 and ?b=2&a=1 are one entry, not two copies of one answer.
None is dropped"Absent" and "explicitly null" collapse together — they return the same body, so they share a key.
limit is normalisedHashed as the resolved integer, so ?limit=3 and an omitted limit — byte-identical responses — do not get stored twice.
Collisions64-bit truncated SHA-256. Birthday bound: 50 % at ~232 keys for one path; the real space is a handful of combinations per asset.
Schema changesThe namespace is versioned. A planned change bumps v1→v2; an unplanned one is caught at read time — a payload that no longer validates is treated as a miss and deleted, so no instance can ever serve a validation error out of the cache.
The identity is real user data, so it is glob-escaped before SCAN MATCH. An asset published at /media/*.m3u8 would otherwise match half the keyspace and one publish would wipe the cache.

Two endpoints cached, three refused

The refusals are the defensible part — caching everything is not a design.

✓ GET /routing/resolveRead on every client download; 3 queries, the last a 3-table join whose ORDER BY is a computed score, so no index can serve it. Cost is paid per read, inputs change per write, reads vastly outnumber writes — that is the definition of a cacheable read.
✓ GET /stats/networkSix grouped aggregates over the largest tables, read by dashboards, changes slowly. Nobody decides anything on a fresher fleet summary.
✗ POST /heartbeatThe write hot path. Caching a write is meaningless.
✗ GET /assetsThe key space is the product of every filter and page offset — poor hit ratio, expensive invalidation.
✗ GET /purges/{id}Polled precisely to watch a counter change. Caching it would break the feature.

TTL: 10 seconds, and not because it is a round number

route:{path}min(asset.cache_ttl_seconds, 10 s) — bound by fleet freshness, not content freshness. The answer embeds heartbeat-derived eligibility and per-node load, so it must not outlive one HEARTBEAT_INTERVAL_SECONDS.
stats:network30 s, by business tolerance. Expiration only — never invalidated.
BothJittered down by 0–10 %. Upward jitter would breach the ceiling, and the ceiling is a correctness statement, not a performance knob.
Seeded assets declare TTLs from 300 s to 7 days, so the 10 s ceiling is always what binds — never the asset's own value. The freshness constraint comes from the fleet, not from the content.
Measured trade-off: TTL 10 s → hit ratio 99.8 %. TTL 60 s → 100.0 %. Six times the TTL bought 0.2 points. At this request rate the key is re-read far more often than it expires, so the short TTL is free — there is nothing to trade freshness for.

Invalidation

Every mutation that changes a cached answer drops it — after the commit. Invalidating before would let a concurrent reader refill the key from the old row.

The trailing colon is load-bearing. The scope for /static/app.bundle.js is cdn:v1:route:/static/app.bundle.js:. Without it, publishing that asset would also evict /static/app.bundle.js.map.
The heartbeat decision — the one that makes the cache viable. Every node heartbeats every 10 s. Dropping the route keyspace on every sample would mean ~1.3 fleet-wide SCANs per second at 13 nodes and ~1 000/s at 10 000 — the hit ratio would sit near zero and the invalidations would synchronise every miss into exactly the stampede the cache exists to prevent. So only a real transition invalidates:
 
• crossing the overload threshold, draining, recovering → eligibility changes → invalidate
• load drifting 22 % → 24 % → only ranking changes → leave it to the TTL

The third metric

The lab asks for hit / miss / invalidation. The first two are in X-Cache on every response. An invalidation belongs to a write, has no response header of its own, and is the one a reader cannot see — so it is logged.

cache.invalidated prefix=cdn:v1:route:/static/app.bundle.js: keys_dropped=1 invalidations_total=1

Scope, how many entries actually went, a per-instance running total, and which instance did it. keys_dropped=0 is a common and correct outcome — the TTL had already expired the entry. That is the expiration-versus-invalidation split visible in a log line.

The p99 rose, and that is reported rather than hidden. The cache did not make the tail worse — it moved the measurement to a higher load point. The same 64 users now push 44 % more requests through the same three single-worker instances. Being able to say that is the point of measuring percentiles instead of averages.
Rows returned, not transactions committed. xact_commit was the obvious metric and it is the wrong one: a read-only transaction is rolled back when its session closes, so that counter mostly tracks the agent simulator's heartbeats and says nothing about the read path. The expensive ranked join was replaced by a key lookup — that is what tup_returned shows and xact_commit hides.
Distributed, not per-process. The entry was stored by one instance and served by all three. An in-process cache would have given three independent copies, three times the misses, and no way to invalidate the other two.

When Redis dies

docker compose … stop redis with traffic flowing.

t = 0 Redis container stopped mid-load.
824 ms Every instance is reporting X-Cache: BYPASS — breakers open, Redis no longer consulted at all.
0–15 s 0 errors. Every status is 200; throughput settles at 226 req/s — exactly the uncached baseline, not a degraded version of it.
restart First read MISS, next HIT. The cache refills itself — no API restart.
after Recovery is staggered, per instance: each owns its own breaker, so one is already serving hits while another still answers BYPASS.
1. Fail-open at the boundaryThe cache-aside layer swallows backend failures and falls through to PostgreSQL — enforced in one place, not left to each backend. A test that injected a raising backend found a real bug here: a cache error escaping invalidate turned a perfectly good POST /heartbeat into a 500.
2. A circuit breakerAfter N consecutive failures the backend stops consulting Redis for a cooldown. Without it every request would pay the 250 ms socket timeout — the fallback would be functional but roughly an order of magnitude slower. The breaker is what makes this graceful rather than merely survivable.
3. Honest headersWhile the breaker is open the backend reports itself disabled, so X-Cache says BYPASS — "not consulted" — instead of a misleading MISS.

Theory, one line each

Why cache-aside and not the other three
Cache-Aside — chosenApp reads the cache, falls back to the DB on a miss, then stores. The cache is never in the write path.
Read-ThroughNeeds a cache that can run the query. A 3-table ranked join is not something Redis can load for us.
Write-ThroughThere is nothing to write. A route resolution is a derived result — no single write produces it; it is a function of an asset, the fleet's heartbeats and the distribution rules.
Write-BehindWould put a cache in the durability path of a system of record. Losing Redis would lose committed data.
Stampede / thundering herd — measured, and deliberately not mitigated

N concurrent misses on one hot key become N identical queries. Measured: 64 users on a flushed key produced 3 misses — one per instance, 99.9 % hit ratio — because the loader takes ~2 ms. The herd is bounded by the instance count, not by concurrency.

A single-flight lock earns its place when loader_cost × concurrency exceeds the database burst you can absorb. At 3 extra queries per TTL window it does not — and an unmeasured mitigation is worse defence material than a measured problem. A per-instance asyncio.Lock would also only have reduced the herd 3-fold, since each instance misses independently; solving it across the pool needs a lock in Redis, which reintroduces the very dependency the fail-open design just removed.
Avalanche — mitigated

Many keys expiring in the same instant, sending a synchronised wave at the database — classically after a bulk warm-up or an invalidation burst. Every TTL is jittered down by up to 10 %, which spreads the wave. A cold Redis restart is an avalanche by another name, covered by the same fail-open path plus the breaker.

Not the same problem as a stampede: a stampede is many clients on one key, an avalanche is one client pattern across many keys. Jitter fixes the second and does nothing for the first — which is why they are answered separately.

Eviction — allkeys-lru, 256 MB
LRU — chosenEvicts least recently used. Matches a recency-skewed workload: a release makes one path hot for minutes, then it cools.
LFUEvicts least frequently used — would keep long-dead popular paths resident while evicting a path that just became hot.
RandomNo reason to prefer it.
noevictionWrites fail at the limit — turning a full cache into failing writes is unacceptable for an optimisation.

allkeys- rather than volatile- because every key written here already carries a TTL, which makes them equivalent today while keeping the policy correct if one is ever written without one.

Expiration vs invalidation — this system uses both, on purpose

A failed invalidation degrades to bounded staleness, not permanent staleness — the entry still expires on its TTL. That is the second reason the ceiling is short: it is the backstop for a cache that was unreachable at the moment a write committed.
Does the cache break statelessness? No — and that is the point

An in-process cache would be the textbook violation. This one is shared external state, in the same category as PostgreSQL:

Any instance, any requestServed from the same entry — proven live: stored by one, served by three.
Kill an instanceNo cache content is lost.
The only new per-process objectA Redis connection pool — same category as the SQLAlchemy pool.
The one genuinely local pieceEach backend's circuit breaker — health information about that instance's link to Redis, not business data. Which is exactly why recovery is staggered.

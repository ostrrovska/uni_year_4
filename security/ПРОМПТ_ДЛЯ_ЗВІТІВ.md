## КОНТЕКСТ: що це за роботи

| | ЛР6 | ЛР7 |
|---|---|---|
| Тема | Аутентифікація користувачів на основі токенів безпеки | Підсистема керування доступом |
| Варіант | **2** — проста парольна аутентифікація за хеш-образами | **1** — довірче (дискреційне) керування доступом |
| Що вирішує | **хто** звертається до системи | **що** йому дозволено |

Це **одна наскрізна програма**: сервер ЛР7 імпортує модуль аутентифікації `common/authcore.py`, написаний для ЛР6, і працює з тією самою базою реєстраційної інформації. У звіті ЛР7 цей зв'язок треба підкреслити — за завданням ЛР7 будується «користуючись програмою, розробленою в ході ЛР6».

**Технічна основа:**
- Python 3.13, **тільки стандартна бібліотека** — жодних сторонніх пакетів.
- Уся криптографія — прямі виклики **Microsoft CryptoAPI** (`advapi32.dll`) через `ctypes`. Хешування не підмінене на `hashlib`: контрольний вектор `sha256(b"abc")` дає еталонне `ba7816bf…f20015ad`.
- Токен безпеки — **реальний USB флеш-диск** (14,6 ГБ, відформатований у FAT32, мітка `SECTOKEN`).
- Клієнт і сервер спілкуються по **TCP/IP**: ЛР6 — порт 5607, ЛР7 — порт 5707.
- Відлагоджено через зворотну петлю `127.0.0.1`, потім виконано на двох машинах.

**Дійові особи у протоколах:** `ostrovska`, `shevchenko`, `kovalenko` — зареєстровані суб'єкти; `mallory` — незареєстрований ідентифікатор для негативного тесту. Об'єктів даних — 12.

## КЛЮЧОВІ ФАКТИ, ЯКІ МАЮТЬ БУТИ У ЗВІТАХ

### ЛР6 — склад і захист токена

Файл: `<флешка>:\SECTOKEN\<слот>\token.dat`, розмір 256 байт.

Відкритий зміст (JSON, до шифрування):

| Поле | Призначення |
|---|---|
| `user_id` | ідентифікатор користувача |
| `salt` | 16 випадкових байтів, згенеровані `CryptGenRandom` |
| `pwd_hash` | хеш-образ `SHA256(salt ‖ password)` |
| `created_at` | час реєстрації, для аудиту |

Пароль у відкритому вигляді не зберігається ні на токені, ні на сервері.

**Захист файлу:** формується блок `"SECTOK01" ‖ SHA256(JSON) ‖ JSON` і шифрується **AES-256-CBC** на ключі, похідному від PIN-коду (`CryptDeriveKey` з хешу PIN); випадковий вектор ініціалізації пишеться попереду шифротексту. Це дає конфіденційність, цілісність (тег SHA-256) і швидку перевірку правильності PIN (сигнатура).

**Обговорення стійкості — обов'язково збалансоване.** Сильні сторони: AES-256 стійкий, випадковий IV ховає однакові дані, тег цілісності не дає непомітно підмінити байт (це підтверджено тестом з інверсією байта). Слабке місце: ключ виводиться з PIN одним хешуванням, а чотиризначний PIN — це 10⁴ варіантів, і сигнатура `SECTOK01` дає зловмиснику миттєвий критерій «вгадав». Отже **практична стійкість файлу дорівнює стійкості PIN, а не довжині ключа AES**. Способи підсилення: повільна функція виведення ключа (PBKDF2/scrypt/Argon2), довга парольна фраза, лічильник невдалих спроб, апаратний токен, прив'язка до серійного номера носія.

### ЛР6 — використані функції CryptoAPI

Обов'язково таблицею:

| Операція | Виклики CryptoAPI | Де застосовано |
|---|---|---|
| SHA-256 | `CryptAcquireContextW` → `CryptCreateHash(CALG_SHA_256)` → `CryptHashData` → `CryptGetHashParam(HP_HASHVAL)` → `CryptDestroyHash` | хеш-образ пароля, тег цілісності |
| Генерація випадкових чисел | `CryptGenRandom` | сіль користувача, вектор ініціалізації |
| Виведення ключа | `CryptDeriveKey(CALG_AES_256)` з хеш-об'єкта | ключ із PIN, ключ каналу |
| Шифрування | `CryptSetKeyParam(KP_IV)` → `CryptEncrypt` / `CryptDecrypt` | файл токена і мережевий трафік |
| Звільнення ресурсів | `CryptDestroyKey`, `CryptReleaseContext` | — |

Провайдер — **`PROV_RSA_AES` (тип 24)** з прапорцем `CRYPT_VERIFYCONTEXT` (тимчасовий контекст без постійного ключового контейнера).

### ЛР6 — протокол має показати п'ять різних результатів

1. **Вдала аутентифікація** — хеш-образ збігся з базою.
2. **Невірний PIN** — файл на токені не розшифровується; до сервера запит **не йде взагалі**.
3. **Підроблений токен** — правильний ідентифікатор, але хеш-образ іншого пароля → «hash image does not match the database».
4. **Незареєстрований ідентифікатор** → «unknown identifier 'mallory'».
5. **Пошкоджений файл токена** (інвертовано один байт) → спрацював контроль цілісності.

Пункт 2 варто окремо прокоментувати: відмови через невірний PIN у серверному журналі немає, бо перший рубіж оборони спрацював на боці клієнта.

### ЛР6 — прогін на двох машинах

Сервер на хості `192.168.31.232`, клієнт у віртуальній машині VirtualBox `192.168.31.76` (мостовий адаптер, обидві адреси від роутера). У віртуальну машину **нічого не встановлювалось**: на флешці поряд із токенами лежали Python embeddable і код, клієнт запускався прямо з токена.

Показова деталь: у віртуальній машині токен отримав літеру **`E:`** замість `D:`, і автовизначення знайшло його без налаштувань, бо пошук іде **за типом пристрою** (`GetDriveTypeW` = `DRIVE_REMOVABLE`), а не за літерою.

Доказ розподіленого запуску — поле `peer` у серверному журналі містить адресу віртуальної машини, а не `127.0.0.1`.

### ЛР7 — модель і структури даних

Матрична модель Д. Деннінг ⟨S, O, A⟩: S — суб'єкти (активні), O — об'єкти (пасивні), A — матриця доступу; рядок = суб'єкт, стовпчик = об'єкт, клітинка = права.

Матриця розріджена, тому зберігається як **списки доступу (ACL)** — файл `acl.json`:

```json
{
  "objects": {
    "finance_q1": {
      "owner": "ostrovska",
      "acl": { "shevchenko": ["read"], "kovalenko": ["grant"] },
      "created_at": "2026-10-13T17:36:31"
    }
  }
}
```

Ключ зовнішнього словника — об'єкт, тобто **стовпчик** матриці. Власник винесений окремим полем: його повний набір прав не зберігається, а виводиться з факту володіння. **Список повноважень** (рядок матриці) обчислюється на льоту методом `capability_list()`. Команда `rights <obj>` показує стовпчик, `caps` — рядок, `matrix` — усю матрицю.

Порожні клітинки у структурі просто відсутні — пам'ять витрачається лише на реально видані права.

### ЛР7 — права доступу (таблицею)

| Право | Що дозволяє | Хто має за замовчуванням |
|---|---|---|
| `read` | прочитати вміст об'єкта | власник |
| `write` | дописати до об'єкта | власник |
| `delete` | видалити об'єкт | власник |
| `grant` | надавати й відкликати права інших на цей об'єкт | власник |
| `own` | право власника: повний контроль над стовпчиком матриці, передача володіння | творець об'єкта |

Правила, які перевіряє сервер: власник завжди має всі п'ять прав · решта — лише явно записані в ACL · змінювати права може той, у кого є `grant` · передати володіння може **тільки** власник · права власника не відкликаються · хто створив об'єкт, той його власник.

### ЛР7 — головний результат експерименту (сесія S5)

Це найцінніша частина звіту, виділи її окремо.

Власниця `ostrovska` видала `kovalenko` **лише** право `grant` на об'єкт `finance_q1`, без права `read`. Далі в журналі:

```
read finance_q1                  → DENIED   немає права read
grant finance_q1 kovalenko read  → ALLOWED  бо є право grant
read finance_q1                  → ALLOWED  сам собі видав право
grant finance_q1 kovalenko own   → DENIED   володіння передає лише власник
```

**Висновок:** делегування права керувати правами фактично дорівнює передачі всіх прав на об'єкт. Теза про неконтрольоване поширення повноважень у дискреційній моделі підтверджена не переказом підручника, а власним протоколом. Усунути це всередині моделі неможливо — потрібен перехід до адміністративного (мандатного) керування. При цьому межа все-таки проведена: право власника залишилось захищеним.

Звіт ЛР7, три рисунки:

1. **Діаграма прецедентів.** Актори: *Власник об'єкта*, *Інший користувач*. Прецеденти: пройти аутентифікацію за токеном, створити об'єкт, читати об'єкт, писати в об'єкт, видалити об'єкт, надати або відкликати право, передати володіння, переглянути матрицю доступу, перевірити права й запротоколювати. Операції з правами й передача володіння доступні лише власнику; усі операції з об'єктами включають перевірку прав.
2. **Діаграма модулів.** `client.py` → `netproto.py` (AES-256 над TCP) → `server.py`; сервер звертається до `common/authcore.py` (а той до `server_db.json` з ЛР6) і до `acl.py` (а той до `acl.json` зі списками доступу та до текстових об'єктів у `storage/`); обидві сторони пишуть у `protolog.py`. Підкресли візуально, що модуль аутентифікації взято з ЛР6.
3. **Блок-схема перевірки доступу.** Команда від клієнта → чи аутентифікована сесія → чи існує об'єкт → чи суб'єкт є власником (так → має всі п'ять прав; ні → читаємо список доступу й перевіряємо потрібне право) → чи операція змінює права (якщо це передача володіння — додаткова перевірка «суб'єкт є власником») → виконання операції → результат і запис у протокол. Усі гілки відмови сходяться в той самий фінальний блок.

**Вимоги до вигляду:** підписи українською; жодних вигаданих елементів, яких немає в описі вище; стрілки не перетинають блоки; текст не вилазить за межі рамок; однотипні блоки оформлені однаково. Заголовок рисунка має казати, що саме він показує, а не просто називати тему.

# Лабораторна 3: конкурентний pipeline обробки даних у Go

Консольний застосунок на Go, що обробляє числові задачі за схемою
`Producer → Jobs channel → Worker Pool → Results channel → Aggregator → Output`.
Мета — на практиці застосувати `sync.WaitGroup`, `context.Context` і `select`
для керування конкурентним пулом воркерів і коректного завершення роботи.

Розширені результати й аналіз — у [RESULTS.md](RESULTS.md).
Цей файл самодостатній: теорія, що зроблено, запуск, результати, висновки.

---

## 1. Теорія, яку перевіряємо

### Pipeline як композиція незалежних стадій

Кожна стадія (producer, worker, aggregator) — окрема goroutine (або пул
goroutine), що спілкується із сусідніми стадіями **лише через channel**, без
спільної змінної стану. Це головна ідея конкурентності в Go: "не діліться
пам'яттю для комунікації — спілкуйтеся, щоб ділити пам'ять". Завдяки цьому
агрегатор не потребує м'ютекса: він єдиний, хто читає з `results`, і працює
в одній goroutine (`main`), тож гонки даних немає структурно, а не завдяки
блокуванням.

### Чому потрібен і WaitGroup, і закриття channel

`jobs` закриває producer — це сигнал "задач більше не буде", і він дозволяє
кожному worker вийти з `for range`/`select` природно, без зовнішньої команди.
Але `results` не може закрити жоден окремий worker: якщо закрити його з першого
воркера, що завершився, решта воркерів спробують писати в закритий channel і
застосунок впаде з панікою. Тому `results` закриває окрема goroutine, яка
спочатку робить `wg.Wait()` — чекає, поки **всі** воркери завершаться — і лише
тоді закриває channel. `WaitGroup` тут — єдиний спосіб дізнатися "всі воркери
дійсно закінчили", бо жоден канал цього сам по собі не показує.

### context.Context і select — скасування без явних прапорців

Замість булевої змінної `stopped` чи додаткового каналу "скасувати", producer
і worker слухають `ctx.Done()` в `select` поряд з основною роботою. Коли
контекст скасовується (вручну або по `WithTimeout`), `ctx.Done()` повертає
закритий channel, і `select` одразу обирає цю гілку, навіть якщо producer
якраз намагався відправити задачу, а worker — прийняти чи відправити
результат. Це дає коректне часткове завершення: частина задач встигає
обробитись, решта — ні, і jobs/results не лишаються "висіти" назавжди.

### Unbuffered проти buffered channel

Unbuffered channel (`buffer=0`) синхронізує відправника й отримувача: `jobs <-
job` блокується, поки якийсь worker не буде готовий прийняти саме цю задачу.
Buffered channel дозволяє producer-у "піти вперед" на розмір буфера, не
чекаючи, поки воркери розберуть попередні задачі. Це зменшує кількість
переключень контексту між goroutine, і саме тому буферизація прискорює
прогін навіть без зміни кількості воркерів (розділ 2 результатів нижче).

### go run -race — що саме перевіряє

Детектор гонок (`-race`) інструментує кожен доступ до пам'яті та ловить
ситуацію "дві goroutine звертаються до однієї адреси, і хоча б одна —
на запис, без синхронізації між ними". У цьому застосунку воркери не мають
спільного стану (кожен отримує свою копію `Job` з channel), а агрегатор працює
в одній goroutine — тобто структурно гонок бути не повинно. `-race` тут —
підтвердження того, що архітектура справді не ховає прихованого спільного
стану, а не пошук конкретного бага.

## 2. Що побудовано

| Файл | Роль |
|---|---|
| `go-service/pipeline.go` | `Job`, `Result`, `Stats`, `producer`, `worker`, `runPipeline` — сам pipeline |
| `go-service/table.go` | Рендер рівних Unicode-таблиць для виводу в консоль |
| `go-service/main.go` | CLI: режим матриці запусків (за замовчуванням) і режим одного кастомного прогону |
| `demo.ps1` | Один командний файл: збирає бінарник, показує матрицю й демонстрацію скасування |

Задача: `Job{ID, Value}`. Обробка: `result = Value*Value + burn(iterations)`,
де `burn` — невелике навантажувальне обчислення (сума залишків у циклі), яке
додає відчутну CPU-вартість на задачу, щоб кількість воркерів дійсно впливала
на час виконання, а не губилась на накладних витратах каналів. `burn` завжди
повертає однакове число для фіксованої кількості ітерацій, тож очікувана сума
результатів для `N` задач обчислюється наперед (`expectedSum`) і звіряється з
тим, що реально зібрав агрегатор — колонка `Check` у таблицях нижче.

CLI-прапорці: `-tasks`, `-workers`, `-buffer`, `-cancel-after` (запускає
`context.WithTimeout` і демонструє шлях скасування через `select`).

## 3. Як відтворити

Один скрипт збирає бінарник і показує все: матрицю з трьох таблиць і
демонстрацію скасування.

```powershell
cd C:\uni_year_4\node_go\lab_3
.\demo.ps1
```

Запустити лише матрицю вручну, без скрипта:

```powershell
cd C:\uni_year_4\node_go\lab_3\go-service
go run .
```

Ручний прогін з власними параметрами:

```powershell
go run . -tasks 5000 -workers 8 -buffer 100
```

Демонстрація скасування (частина задач не встигає обробитись):

```powershell
go run . -tasks 2000 -workers 4 -buffer 10 -cancel-after 1ms
```

Перевірка на гонки даних (потребує C-компілятор, напр. MinGW-w64 gcc, бо
`-race` лінкує TSan-рантайм через cgo). `demo.ps1` намагається запустити її
напряму на Windows, а якщо компілятора нема — автоматично падає назад на
WSL (`gcc` там уже є), і таблиця результату все одно друкується в тому ж
прогоні:

```powershell
go run -race . -tasks 2000 -workers 8 -buffer 10
```

## 5. Висновки

**1. Воркери масштабуються до кількості ядер, далі — деградація.**
На машині з 12 логічними ядрами пропускна здатність росте аж до 8 воркерів
(501 570 jobs/s), а на 16 — падає (443 398 jobs/s): воркерів стає більше за
вільні ядра, і планувальник ОС починає перемикати контекст замість реальної
паралельної роботи.

**2. Буфер прибирає накладні витрати на синхронізацію, не на обчислення.**
Той самий обсяг роботи (10000 задач, 8 воркерів) пришвидшується з 21.0 до
9.7 мс лише від збільшення буфера з 0 до 1000 — більш ніж удвічі. Це не
прискорення самого обчислення, а усунення блокувань producer-а і воркерів
одне на одного при кожній окремій задачі.

**3. Пропускна здатність не лінійна за кількістю задач.**
100 задач — надто мало, щоб витрати на запуск goroutine і каналів себе
окупили (вимірюється як "<0.1 мс", нижче роздільної здатності таймера).
Від 1000 до 10000 jobs/s зростає (goroutine-пул "розганяється"), а на 100000
трохи просідає — працює довше, ніж встигає "прогрітися" переваги буфера.

**4. Коректність перевіряється арифметично, а не лише відсутністю паніки.**
Колонка `Check` звіряє суму результатів з детерміновано обчисленим
очікуваним значенням. Це ловить саме ті помилки конкурентності, які не
падають з панікою, а мовчки гублять або дублюють задачі (наприклад, якщо
`results` закрити заздалегідь).

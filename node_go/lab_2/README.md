# Лабораторна 2: моделі конкурентності Node.js та Go

Два однакові за функціями HTTP-сервіси — один на Node.js, другий на Go — під
однаковим навантаженням. Мета: побачити на числах, чим відрізняються їхні моделі
виконання і де кожна з них виграє.

Детальний звіт із розширеними коментарями — у [RESULTS.md](RESULTS.md).
Цей файл — самодостатній: теорія, що зроблено, результати, висновки.

## 1. Теорія, яку перевіряємо

### Конкурентність і паралелізм — різні речі

**Конкурентність** — здатність мати багато незавершених задач одночасно.
**Паралелізм** — фізично виконувати їх у той самий момент на різних ядрах.

Node.js конкурентний, але не паралельний на власному коді. Go — і те, і те.
Уся лабораторна побудована навколо цієї різниці.

### Node.js: один потік і event loop

JavaScript у Node виконується **в одному потоці**. Асинхронність дає event loop —
цикл, який по черзі дістає з черги готові колбеки і виконує їх у цьому єдиному потоці.

Коли код робить `setTimeout` або читає сокет, операція віддається операційній
системі, а колбек ставиться в чергу на момент, коли результат буде готовий. Потік
при цьому вільний і обслуговує інші запити. Саме тому один потік Node спокійно
тримає сотні одночасних з'єднань.

Але синхронний цикл `for (let i = 0; i < 2e9; i++)` такої точки передачі керування
**не має**. Він володіє потоком, доки не завершиться. Усе, що прийшло за цей час, —
і нові важкі запити, і найлегша перевірка стану — лежить у черзі. Це називається
**блокуванням event loop**, і головний дослід лаби вимірює його тривалість.

### Go: goroutine на з'єднання

Go запускає окрему **goroutine** на кожне вхідне з'єднання (це робить стандартний
`net/http`, без жодних дій з боку розробника). Goroutine — легка одиниця виконання,
якою керує не операційна система, а рантайм Go; вона коштує близько кілобайта стека,
тому їх можуть бути сотні тисяч.

Рантайм тримає пул потоків ОС за кількістю ядер (`GOMAXPROCS`, у нашому випадку 12)
і розкладає goroutine по них. Планувальник **витісняльний**: goroutine, яка довго
рахує, буде примусово знята з ядра, щоб не заморити інші.

Наслідок: важкий цикл займає одне ядро з дванадцяти, решта запитів продовжують
обслуговуватися паралельно.

### Два типи навантаження

- **I/O-bound** — процесор більшу частину часу чекає (диск, мережа, БД). Кількість
  ядер майже не важлива; важливо дешево тримати багато відкритих очікувань.
- **CPU-bound** — все вирішує швидкість обчислень і кількість задіяних ядер.

Гіпотеза, яку перевіряємо: на I/O моделі будуть близькі, на CPU однопотокова
модель програє принципово.

## 2. Що побудовано

| Каталог | Що це |
|---|---|
| `node-service/` | Node.js, порт `3000`, лише стандартна бібліотека |
| `go-service/` | Go, порт `8080`, лише стандартна бібліотека |
| `bench/` | Сценарії k6, монітор ресурсів, скрипт повного прогону |

Обидва сервіси реалізують однаковий набір маршрутів:

| Маршрут | Node | Go | Роль в експерименті |
|---|---|---|---|
| `GET /health` | + | + | Миттєва відповідь. Проба живучості: чи відповідає сервіс, поки зайнятий |
| `GET /io` | + | + | Асинхронна затримка 100 мс (`setTimeout` / `time.Sleep`). Імітація I/O |
| `GET /cpu` | + | + | Важкий цикл, `chunks` штук **послідовно**. CPU-навантаження |
| `GET /cpu-goroutines` | — | + | Ті самі цикли, кожен в окремій goroutine |
| `GET/POST/PUT/DELETE /items` | + | + | CRUD з лабораторної 1 |

Параметри: `/io?ms=100`, `/cpu?n=50000000&chunks=4`.

Ключова деталь: `/cpu` і `/cpu-goroutines` виконують **однаковий обсяг роботи**.
Різниця лише в тому, послідовно чи паралельно виконуються цикли — тому їх коректно
порівнювати між собою.

Цикл у обох мовах повертає накопичену суму, і ця сума потрапляє у відповідь. Без
цього і V8, і компілятор Go викинули б цикл як мертвий код, і ми міряли б порожнечу.

## 3. Чим міряємо

**k6** — генератор HTTP-навантаження від Grafana Labs. Сценарій описується на
JavaScript, k6 виконує його багатьма паралельними «віртуальними користувачами»
і рахує статистику по кожному запиту. Написаний на Go, тому сам не стає вузьким
місцем — на відміну від циклу в PowerShell, який робить запити послідовно.

- `bench/blocking.js` — головний дослід: один важкий `/cpu` під рівним потоком
  `/health` (10 запитів/с, 10 с)
- `bench/load.js` — навантажувальний прогін для порівняльної таблиці
- `bench/monitor.ps1` — семплер CPU і RAM процесу; k6 бачить лише клієнтський бік,
  тому споживання ресурсів міряється окремо
- `bench/run-all.ps1` — робить усі вісім прогонів і збирає підсумкові таблиці

### Мінімум термінів, щоб читати таблиці

| Термін | Значення |
|---|---|
| **RPS** | Запитів **завершено** за секунду. Пропускна здатність |
| **VU** | Virtual user — одна паралельна послідовність запитів. 50 VU = 50 одночасних клієнтів |
| **avg** | Середня затримка. Найслабше число: один викид розмазується по сотні швидких запитів |
| **med (p50)** | Медіана — «типовий» запит |
| **p95 / p99** | 95 % (99 %) запитів були швидші за це значення. Показує хвіст розподілу, за ним пишуть SLA |
| **CPU %** | Відсоток **одного** ядра. 100 % = одне ядро зайняте повністю, 1200 % = усі 12 ядер машини |

Розбіжність між med і p95 сама по собі діагноз: якщо вони відрізняються на порядки,
запити діляться на дві різні групи, а не рівномірно повільнішають.

## 4. Як відтворити

Обидва сервіси мають працювати. Go запускається **зібраним бінарником**, а не через
`go run .`: той компілює програму в тимчасовий файл і запускає її дочірнім процесом,
тож монітор чіплявся б до обгортки, а не до самого сервера.

```powershell
# Термінал 1
cd C:\uni_year_4\node_go\lab_2\node-service
npm start

# Термінал 2
cd C:\uni_year_4\node_go\lab_2\go-service
& "C:\Program Files\Go\bin\go.exe" build -o bin\go-service.exe .
.\bin\go-service.exe
```

Потім один скрипт робить усе: три досліди з блокуванням, п'ять навантажувальних
прогонів, паралельний замір CPU/RAM, підсумкові таблиці.

```powershell
cd C:\uni_year_4\node_go\lab_2\bench
.\run-all.ps1            # ~4 хв
.\run-all.ps1 -Quick     # ~2 хв, прогони по 10 с — для репетиції
```

Результат — у `bench/results/`: `summary.md` з таблицями і сирі метрики в JSON.
Покрокові команди для ручних прогонів — у [додатку](#додаток-ручні-прогони).

## 5. Результати

Обладнання: Windows 10, 12 логічних ядер, Node v22.16.0, Go 1.27.0.

### Дослід 1. Блокування event loop

Один запит `/cpu` (2 млрд ітерацій × 4 цикли) під рівним потоком `/health`.

| Сервіс | Ендпойнт CPU | `/cpu`, мс | `/health` avg, мс | `/health` p95, мс | `/health` max, мс |
|---|---|---|---|---|---|
| Node.js | `/cpu` | 5990 | 1596 | 5588 | 5892 |
| Go | `/cpu` | 2019 | 0.6 | 1.1 | 1.7 |
| Go | `/cpu-goroutines` | 515.2 | 0.7 | 1.1 | 1.7 |

Найдовша проба на Node чекала 5892 мс — практично рівно стільки, скільки тривав
сам цикл (5990 мс). Медіана при цьому лишилася 0.96 мс: запит або проходить миттєво,
або чекає повного завершення циклу.

Окремий наслідок: за 10 с k6 мав відправити 100 проб, а відправив 62. Решта не
стартувала взагалі — усі віртуальні користувачі стояли заблокованими. Реальна
недоступність гірша, ніж показує колонка avg.

### Дослід 2. Навантажувальне порівняння

| Workload | Runtime | RPS | Avg | p95 | p99 | CPU | RAM |
|---|---|---|---|---|---|---|---|
| I/O | Node.js | 439.4 | 113.6 | 121.4 | 128.9 | 4 % | 32.7 МБ |
| I/O | Go | 491.9 | 101.2 | 102.4 | 103.1 | 8.3 % | 24.3 МБ |
| CPU (послідовно) | Node.js | 6.7 | 1463 | 1512 | 1650 | 94.3 % | 32.9 МБ |
| CPU (послідовно) | Go | 100.6 | 99.1 | 157.4 | 199.6 | 807 % | 23.9 МБ |
| CPU (goroutines) | Go | 116.8 | 85.4 | 125.6 | 151.5 | 1020 % | 23.9 МБ |

### Дослід 3. Дві версії `/cpu` у Go

| Версія | Одиночний запит, мс | RPS під навантаженням | CPU |
|---|---|---|---|
| Послідовна (`/cpu`) | 2019 | 100.6 | 807 % |
| Goroutines (`/cpu-goroutines`) | 515.2 | 116.8 | 1020 % |

## 6. Висновки

**1. Node не просто повільніший на CPU — він серіалізує запити.**
При 10 одночасних клієнтах середня затримка 1463 мс, RPS 6.7. Один запит коштує
1/6.7 ≈ 150 мс (і мінімальний виміряний час — 150.2 мс), а 10 × 150 = 1500 ≈ 1463.
Це формула черги з **одним** обслуговуючим пристроєм: запити стоять один за одним.
У Go avg (99.1 мс) практично дорівнює вартості одного запиту — клієнти
обслуговуються одночасно.

**2. Розрив ×15 складається з двох різних причин.**
Node зайняв 94.3 % одного ядра, Go — 807 %, тобто у 8.6 раза більше процесорного
часу. Але RPS відрізняється у 15 разів. Решта (×1.7) — швидкість самого циклу:
на однаковій роботі 2019 мс проти 5990 мс, приблизно 0.25 нс на ітерацію проти
0.75 нс у V8. Вирішальна причина — ядра, але приписувати весь розрив моделі
конкурентності було б неточно.

**3. На I/O моделі майже рівні.**
439 проти 492 RPS — різниця 12 %, при вдвічі меншому споживанні процесора у Node.
При заданій затримці 100 мс Node додає 13.6 мс власних накладних, Go — 1.2 мс.
Node програє тут не архітектурно, а на дрібних накладних: `setTimeout` не займає
потік, тому єдиному потоку нічого не заважає.

**4. Goroutines прискорюють запит, але не пропускну здатність.**
Одиночний запит: 2019 → 515 мс, це ×3.92 при 4 goroutine — майже ідеальне лінійне
прискорення. Під навантаженням же лише +16 % RPS, причому ціною 1020 % CPU замість
807 %. Причина: при 10 одночасних запитах ядра вже завантажені самими запитами,
паралелити всередині кожного нема куди. Виграш лишається в хвості затримки
(p95 125.6 проти 157.4 мс).

Практичне правило: дробити роботу всередині запиту варто, коли запитів мало, а
критична затримка кожного. При високій конкурентності джерелом паралелізму є самі
запити.

**5. Пам'ять тут не аргумент.** 33 МБ проти 24 МБ — на тлі ×15 по RPS це шум.

### Коли яка модель вигідніша

**Node.js** — на I/O-bound навантаженні: очікування бази, файлів, зовнішніх API.
Там потік простоює, і один потік обслуговує сотні з'єднань. Ціна моделі: будь-яке
довге синхронне обчислення зупиняє весь сервіс, тому таку роботу виносять у
`worker_threads`, окремі процеси (`cluster`) або зовнішню чергу.

**Go** — на CPU-bound і змішаному навантаженні: паралелізм дається без окремих дій
розробника, і один повільний обробник не впливає на решту. Ціна — складніша мова
й необхідність думати про синхронізацію спільних даних, чого в однопотоковому
Node не існує за визначенням.

## Додаток: ручні прогони

Потрібні, якщо показуєш експеримент покроково замість `run-all.ps1`.

### Дослід із блокуванням

```powershell
cd C:\uni_year_4\node_go\lab_2\bench

# Node
k6 run --quiet --log-format=raw --log-output=stdout -e BASE_URL=http://localhost:3000 blocking.js

# Go, послідовна версія
k6 run --quiet --log-format=raw --log-output=stdout -e BASE_URL=http://localhost:8080 blocking.js

# Go, версія на goroutines
k6 run --quiet --log-format=raw --log-output=stdout -e BASE_URL=http://localhost:8080 -e CPU_PATH=/cpu-goroutines blocking.js
```

Прапорці для демонстрації: `--quiet` прибирає смужку прогресу, `--log-format=raw`
друкує `health: 12 ms` замість рядка з міткою часу й рівнем логування,
`--log-output=stdout` кладе ці рядки в той самий потік, що й підсумкову таблицю.

Поки цикл крутиться, у Node термінал **мовчить**, а потім вивалює накопичену чергу.
Наприкінці k6 друкує таблицю з вердиктом:

```
┌────────────────────────────────────────────────────────────────┐
│ Node.js  ·  /cpu  ·  n=2 млрд  ·  /health 10/с                 │
├────────────────────────────────────────────────────────────────┤
│ Тривалість CPU-запиту, мс                                 5990 │
├────────────────────────────────────────────────────────────────┤
│ /health avg, мс                                           1596 │
│ /health p95, мс                                           5588 │
│ /health max, мс                                           5892 │
├────────────────────────────────────────────────────────────────┤
│ Проб повільніше за 100 мс                              20 з 62 │
└────────────────────────────────────────────────────────────────┘
  event loop заблоковано: 20 з 62 проб чекали, найдовша — 5892 мс
```

Обсяг навантаження змінюється через `-e CPU_N=...` (дефолт — 2 млрд на кожен
з 4 циклів: близько 6 с на Node і 2 с на Go).

### Навантажувальні прогони

`k6` і `monitor.ps1` запускаються **одночасно** у двох терміналах; pid сервіс
друкує при старті.

```powershell
# Термінал A
k6 run --quiet -e BASE_URL=http://localhost:3000 -e ENDPOINT=/io -e VUS=50 -e DURATION=30s load.js

# Термінал B
.\monitor.ps1 -ProcessId <pid сервісу> -DurationSec 32
```

| # | BASE_URL | ENDPOINT | VUS | DURATION |
|---|---|---|---|---|
| 1 | `http://localhost:3000` | `/io` | 50 | 30s |
| 2 | `http://localhost:8080` | `/io` | 50 | 30s |
| 3 | `http://localhost:3000` | `/cpu` | 10 | 30s |
| 4 | `http://localhost:8080` | `/cpu` | 10 | 30s |
| 5 | `http://localhost:8080` | `/cpu-goroutines` | 10 | 30s |

Для I/O береться більше віртуальних користувачів, бо запити майже нічого не
коштують; для CPU — менше, інакше Node стане в чергу на десятки секунд. Головне:
**для одного рядка таблиці параметри в Node і Go однакові**.

Кожен прогін наприкінці друкує свій рядок таблиці у markdown; колонки CPU і RAM
беруться з виводу `monitor.ps1` (`CpuPercentOfCore`, `PeakRamMB`).

Balancing algorithms
Round Robin
Equal share per peer, by request count. Optimal for a homogeneous pool; pathological when one peer is slow, because it keeps receiving its full 1/N share while its queue grows.
Least Connections
Fewest in-flight requests wins, so a slow peer stops being fed as soon as its work piles up. In nginx OSS the count is per worker, which is why this pool runs one worker.
Weighted Round Robin
Share proportional to configured weight — for genuinely heterogeneous hardware. On an even pool it only concentrates load.
IP Hash
Affinity by client address. nginx hashes the first three octets, so a whole /24 — and everything behind one NAT — lands on a single peer.
Health checks: passive vs active
Passive (nginx OSS)
max_fails / fail_timeout plus proxy_next_upstream. Learns of a failure only by failing a real request, then retries it on another peer so the client sees no error. Cannot see an instance that is listening but broken.
Active (HAProxy)
option httpchk GET /health/ready on a timer. Removes a peer before any client request reaches it — the only mechanism that catches "alive but cannot reach the database".
Liveness vs readiness
/health answers "the process runs" and must not touch the database, or a database blip would restart the fleet. /health/ready answers "this instance can serve traffic" and is what a balancer polls.
The balancer is now the single point of failure
Keepalived / VRRP
Active-passive pair sharing a floating IP; sub-second failover, needs L2 adjacency, one node idle.
DNS round robin / health-checked DNS
No shared address needed, but failover is bounded by TTL and client-side caching.
L4 ECMP / anycast, or a managed cloud LB
Genuinely horizontal balancer scaling, at operational cost.
Caching patterns and failure modes
Cache-Aside (used here)
The application reads the cache, falls back to the database on a miss and stores the result. The cache never sits in the write path, so it can fail without taking writes with it.
Read-through / write-through / write-behind
The cache owns the read or the write. Write-through is wrong for a derived join result like a route resolution: no single write produces it.
Stampede / thundering herd
N concurrent misses on one hot key become N identical queries. Bounded here by a 10 s TTL and a ~2 ms loader; the fix beyond that is single-flight or a lock.
Avalanche
Many keys expiring in the same instant. Mitigated by jittering each TTL downward by up to 10 %.
Eviction: LRU vs LFU
Configured allkeys-lru. This workload is recency-skewed — a release makes one path hot then it cools — and LFU would keep long-dead popular paths resident.
Expiration vs invalidation
Expiration is time-based and needs no coordination; invalidation is event-driven and exact. Here: invalidate on eligibility changes, expire for ranking drift.

# Лабораторна робота №8. Підсистема реєстрації

Доповнення до програми з [ЛР6](../lab_6/README.md) і [ЛР7](../lab_7/README.md):
журнал аудиту, у який потрапляють усі події, що стосуються безпеки.
Звіт писатимемо окремо — тут лише код і як його запускати.

## Що реєструється

| Подія | Коли виникає |
|---|---|
| `AUTH` | будь-яка спроба аутентифікації, вдала й невдала |
| `ACCESS` | читання, запис, видалення об'єкта — дозволені й відхилені |
| `RIGHTS` | надання або відкликання права |
| `OBJECT` | створення об'єкта |
| `SESSION` | відкриття й завершення сесії |
| `SYSTEM` | запуск і зупинка служби |
| `AUDIT` | звернення до самого журналу |

Кожен запис містить те, чого вимагає методичка: порядковий номер, дату й час,
тип події, суб'єкта, об'єкт, саму дію, результат (`SUCCESS`/`FAILURE`), причину
рішення та адресу, звідки прийшов запит.

**Повнота гарантована конструкцією, а не уважністю.** Обидва сервери проходять
аутентифікацію через один модуль `common/authcore.py`, а всі операції доступу —
через одну точку в `lab_7/server.py`, де вже обчислено вердикт. Саме там і стоїть
виклик реєстрації, тож пропустити подію неможливо, не зламавши сам доступ.

## Як захищено журнал

Методичка окремо вимагає захистити журнали від несанкціонованого доступу,
знищення та спотворення. Три механізми, усі на тому ж CryptoAPI, що й токен:

1. **Цілісність.** Кожен запис несе `SHA-256` від хеша попереднього запису і
   власного тіла — записи утворюють ланцюжок. Зміна байта, підміна чи видалення
   запису рве ланцюжок, і `audit_verify.py` називає номер запису, де це сталось.
2. **Конфіденційність.** Кожен запис окремо шифрується `AES-256` на ключі
   аудитора й зберігається одним рядком base64. У блокноті файл — шум.
   Шифрування порядкове, тож журнал лишається дописуваним.
3. **Розмежування доступу.** Прочитати журнал можна лише з ключем, а по мережі —
   лише суб'єктові, якого сервер знає як аудитора (`--auditor`). Відмова іншому
   суб'єктові сама потрапляє в журнал.

## Запуск

```powershell
cd C:\uni_year_4\security\lab_8
.\demo.ps1                        # повний сценарій
.\demo.ps1 -TokenDir C:\temp\tok  # без флешки
```

Або кнопками у вікні `demo.bat` — розділ «Лабораторна 8».

Окремі інструменти:

```powershell
py -3 audit_view.py --tail 20            # показати журнал
py -3 audit_view.py --result FAILURE     # лише невдалі події
py -3 audit_view.py --user shevchenko    # лише один суб'єкт
py -3 audit_verify.py                    # перевірити цілісність
py -3 audit_analyze.py                   # ознаки порушень
py -3 report_table.py                    # таблиця з двох стовпчиків
```

Сервер з увімкненою реєстрацією запускається так:

```powershell
py -3 ..\lab_7\server.py --audit ..\lab_8\logs\audit.jsonl --auditor kovalenko
```

## Що показує демонстрація

1. Реєструються суб'єкти й 12 об'єктів, піднімається сервер з аудитом.
2. Відтворюються всі обов'язкові категорії: вдала й невдала аутентифікація,
   дозволений і відхилений доступ до об'єктів.
3. `shevchenko` намагається прочитати журнал — відмова, яку журнал фіксує.
4. `kovalenko` як аудитор читає журнал **по мережі**.
5. Показано, що файл журналу нечитабельний, а з чужим ключем не відкривається.
6. Ланцюжок перевіряється: цілий → псуємо байт → знайдено запис → видаляємо
   запис → знайдено розрив → відновлюємо → знову цілий.
7. `audit_analyze.py` знаходить сім ознак порушень.
8. `report_table.py` складає таблицю «дія користувача — запис у журналі»
   у `logs/audit_table.md`.

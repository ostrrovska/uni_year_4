Two of those lines are judgement calls. Stable throughput is the best rung that still answered inside p95 < 500 ms with no errors — not the peak, because at saturation throughput is highest and so is the queue behind it. Critical scenario is the one that saturates at the lowest throughput, not the slowest one: it is what breaks first as real traffic grows.

Throughput against offered concurrency

The dashed line is what linear scaling would look like, projected from the first rung. The knee is where the measurement leaves it.

Each point is its own run at constant concurrency, with a 20 s warm-up excluded from the numbers — not a slice of a ramp. A percentile taken across a ramp window is computed over several concurrencies at once and describes none of them.

Median against tail

Logarithmic y-axis, because p50 and p99 differ by one to two orders of magnitude at saturation. On a linear axis the median is a flat line on the baseline and the whole point — that it stayed usable while the tail did not — disappears.

Why the tail grows faster than the mean: a request's latency is its own service time plus the time it spent queued behind others. Below saturation the queue is usually empty, so both are small. Past it, arrivals and service times are variable, so queue length is heavy-tailed — a request that arrives during a momentary burst waits behind every request already there. The mean is dominated by the many requests that found a short queue; p99 is the ones that found a long one, and that population grows super-linearly with utilisation. This is why an average is not a performance specification.

Saturation point

Two panels on one x-axis rather than one frame with two y-scales: requests per second and percent are unrelated units, and overlaying them invites a comparison that means nothing.

Throughput flat while latency grows in proportion to the VU count is the closed-model signature of a saturated system. Little's law says concurrency = throughput × residence time; once throughput is pinned, extra concurrency has nowhere to go but residence time. The knee is where that trade starts.

1 instance against 3

Same ladder, same data, cache disabled in both arms and asserted disabled: the run aborts if a single X-Cache: HIT appears. A cache in front of /routing/resolve makes 1 → 3 look near-linear and hides the limit the experiment exists to find.

The shortfall from 100 % is the resource the instances share. Here that is PostgreSQL and the host's CPU: each instance keeps its own pool, so three instances open three times the connections to one database. Lab 3 measured the same scale-out with a different instrument and landed on 71 % efficiency at three instances — a structural property reproduced twice is worth more than either measurement alone.

Cache disabled, cold, warm

Three states, not two. Disabled never pays the Redis round trip; cold pays it and misses. Reporting only disabled-against-warm charges the round-trip cost to the wrong side.

Clause 2.6 asks for the reduction in load on the DBMS, which is not the same question as response time. The measure is rows returned per request from pg_stat_database — rows rather than committed transactions, because a read-only transaction is rolled back when its session closes, so xact_commit would report that the cache changed nothing.

The primary bottleneck, isolated

/health and /health/ready differ by exactly one thing: readiness takes a connection from the pool and runs SELECT 1. The run alternates between them one request at a time, so each sees half the offered load. Their p95 difference is pool-acquire latency with parsing, routing, serialisation, the balancer and the network all subtracted out.

docs/bottlenecks.md #4 predicted the signature: latency rises while database CPU falls, because the wait happens before any work is done. A SELECT 1 is far too cheap for the query to be the explanation, which is what makes this pair a measurement rather than a correlation.

Coordinated omission

Every ladder run here is a closed model: a fixed number of VUs, each sending its next request only once the previous answered. When the system slows, the generator slows with it — the requests that would have been delayed are never issued, and never measured.

The control is the same requests under constant-arrival-rate, which keeps issuing whether or not the system keeps up and reports dropped_iterations when it cannot. The gap between the two bars is latency that existed in both runs and only one of them counted.

Theory

Saturation point
What it is
The load at which throughput stops rising with offered concurrency. Past it, additional load is converted into queueing rather than work, so latency grows while the system does no more per second than before.
Why throughput goes flat rather than falling
Because the bottleneck resource is already busy 100 % of the time; it cannot do more. It falls only when the queueing itself starts costing — context switching, memory pressure, timeouts that make clients retry work already in flight. A falling curve past the knee is a system in congestion collapse, not merely a saturated one.
Little's law
L = λW: concurrency equals throughput times residence time. In a closed model L is fixed by the VU count and λ is pinned by the bottleneck, so W — what the user feels — is forced to grow linearly in L. That is why the latency curves here are straight lines on the right-hand half of the ladder.
Knee versus cliff
A knee is where the derivative changes; a cliff is where errors begin. They are not the same load, and the gap between them is the headroom a service runs on. This system's knee arrives well before any errors do, which is the comfortable case.
Coordinated omission
The mistake
A closed-loop generator sends its next request only after the previous one answers. When the system stalls, the generator stalls too, so the requests that would have landed during the stall are never sent — and the stall is counted once, by the single request that experienced it, instead of by every request that should have been waiting behind it. The reported distribution is conditioned on the system's own health.
Why it flatters the tail specifically
The median is barely affected: most requests are issued while the system is healthy either way. The omitted requests are exactly the ones that would have been slowest, so the damage is concentrated in p99 — the number most likely to be quoted in an SLO.
The fix used here
An open model: constant-arrival-rate issues at a fixed rate regardless of response, allocating VUs from a pool as responses slow. Its dropped_iterations counter is the honesty check — if it is non-zero, even the open model could not keep up and still understates the queueing.
Why both models are reported
They answer different questions. "What happens with 200 concurrent users?" is a closed question. "What happens when 260 requests a second arrive whether we are ready or not?" is an open one, and it is the one that describes a public endpoint.
Garbage collection, JIT and the percentiles
The classic effect
On a runtime with a stop-the-world collector, a collection pauses every in-flight request at once. The pause is rare, so p50 never sees it, and it is synchronised, so when it does land it lands on everything — a textbook source of a tail that is orders of magnitude above the median while the mean barely moves.
What this system actually has
CPython, which refcounts and has no stop-the-world generational pause of consequence, and no JIT warm-up to speak of. So the GC story here is not the tail's cause, and saying otherwise would be reciting a textbook rather than reading the measurement.
What replaces it
Event-loop scheduling. Each instance runs one uvicorn worker, so one event loop serves every concurrent request on that instance. Any coroutine that does not yield — a synchronous call, a long serialisation, a CPU-bound loop — blocks every other request on that loop for its whole duration. The effect is the same shape as a GC pause (rare, synchronised, invisible to the median, devastating to p99) with a different cause, which is why app/core/fault.py models a CPU-spin and a sleep as two separate knobs: one burns the loop, the other only holds a connection.
And the one that is real here
Pool-acquire wait, measured in the section above, plus PostgreSQL's own checkpoint and buffer-eviction stalls on the write path. Both are queueing, which is the general lesson: tail latency is nearly always a queue somewhere, and the work is finding which one.
Why the warm-up is excluded, and what it warms
SQLAlchemy's pool
Connections are opened lazily. The first requests pay a TCP connect plus PostgreSQL authentication, and pool_pre_ping adds a round trip per checkout until the pool is settled.
asyncpg's statement cache
Each distinct query is prepared once per connection. The first execution on each of up to 20 connections per instance pays that cost.
PostgreSQL's shared buffers
A cold instance reads from disk. The measured buffer hit ratio on these runs is above 98 %, which is only true after the working set is resident.
Redis and the route cache
With a 10 s TTL and 36 route keys, the cache fills in the first seconds. A run that includes those seconds reports a hit ratio and a p99 belonging to neither the cold nor the warm system.
How it is excluded
The warm-up is a separate k6 scenario tagged phase:warmup; every threshold and every figure reads the phase:measure sub-metric. The requests exist in the raw dump and in none of the numbers.
An unpredicted finding: a 503 should not eject a backend
What happened
The first Lab 5 smoke run answered 20831 of 20866 requests with HTTP 502 in 0.000 s, at only 10 VUs, and no application latency was sampled at all.
Why
proxy.conf lists http_503 in proxy_next_upstream, and pools/3.conf ejects a peer after three failures in five seconds. A burst of legitimate 503s — "no eligible node", or under pool exhaustion "no connection available" — therefore takes every peer out of the pool within milliseconds, and nginx answers "no live upstreams".
Why it matters beyond this lab
An application-level 503 means this request cannot be served right now; a connection reset means this backend is dead. Sharing one failure counter between them converts a partial, recoverable overload into a total outage — and does it fastest exactly when the system is already under stress.
What the lab does about it
The load runs use pools/3-lab5.conf, which sets max_fails=0, so the figures describe the application rather than the balancer's health policy. Lab 3's fragments are untouched, since its ejection experiment is the thing they exist for.
Why these three scenarios, and what each one loads
A — read-intensive
GET /routing/resolve at 80 %, the catalogue listing at 12 %, /stats/network at 8 %. Resolve is a multi-table join whose ORDER BY is over a computed score, so it cannot be served from an index; it is the Lab 4 cache target. The catalogue read is deliberately not cached, which keeps a real database floor under the scenario — one that cached to zero would report an infinite speed-up and measure nothing.
B — write-intensive
POST /nodes/{id}/heartbeat: one INSERT into an append-only table plus one UPDATE of the node's own row, in a single transaction. Load reported telemetry stays under the 85 % overload threshold so no heartbeat triggers a status transition — a transition would also invalidate the route cache and make the tail impossible to attribute. Each VU owns one node, because row-lock contention is per-row and a fleet-wide average hides it.
C — complex workflow
Resolve, publish a new asset version, read the purge the publish opened, acknowledge it from three nodes, then read the fleet overview. The publish takes SELECT … FOR UPDATE on the asset and enumerates every targeted node inside the request, which is the O(fleet) work docs/bottlenecks.md #5 predicts will break first.
